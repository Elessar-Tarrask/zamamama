# Architecture — Keystone WhatsApp AI Answerer

AI-администратор на WhatsApp для детского сада Keystone (Алматы). Бот ведёт диалог по сценариям администратора (Даны): приветствует, узнаёт возраст ребёнка, презентует подходящую группу с точными ценами, отвечает на FAQ утверждёнными текстами, мягко задаёт уточняющие вопросы, записывает на экскурсию через Google Calendar, а когда не может помочь — передаёт диалог человеку.

## Общая схема

```
WhatsApp родителя
      │
      ▼
   Wazzup (канал: номер садика)
      │  webhook POST (messages[])                 ▲ POST /v3/message (ответ)
      ▼                                            │
┌─────────────────────────── Firebase (Blaze) ─────┴────────────────────────┐
│                                                                           │
│  wazzupWebhook (HTTP fn)          processConversation (Cloud Tasks fn)    │
│  • проверка секретного токена     • ждёт паузу тишины, склеивает «пузыри» │
│  • дедуп по messageId             • собирает промпт: настройки+FAQ+лид+   │
│  • сохраняет msg → Firestore      │   история диалога                     │
│  • echo-детект ручных ответов     • Azure OpenAI gpt-5-mini + tools       │
│    (isEcho → пауза бота)          • отправляет ответ через адаптер Wazzup │
│  • ставит Cloud Task (+5–12s)     • сохраняет ответ + обновляет лида      │
│                                                                           │
│  Firestore: settings / faq / conversations{+messages} / bookings /        │
│             unanswered / processedWebhooks / sentMessages                 │
│                                                                           │
│  adminSendMessage / adminSetMode (callable fns) ◄── Админ-панель          │
│                                                     (React SPA, Hosting + │
│                                                      Firebase Auth)       │
└───────────────────────────────────────────────────────────────────────────┘
      │ googleapis (сервисный аккаунт)              │ Azure OpenAI REST
      ▼                                             ▼
Google Calendar (календарь экскурсий,        деплоймент gpt-5-mini
расшарен на SA email)                        (endpoint + key заказчика)
```

**Ключевое решение — адаптер провайдера.** Весь код общается с WhatsApp через интерфейс `MessagingProvider` (`functions/src/providers/types.ts`). Сейчас реализация одна — Wazzup. Если когда-нибудь захочется перейти на официальный Meta Cloud API, Green API или self-hosted Evolution API/WAHA — меняется один файл, логика бота не трогается.

## Поток сообщения

1. Родитель пишет → Wazzup делает POST на `wazzupWebhook`. URL содержит секретный токен (`?token=...`); запрос без него получает 403. Handshake-запрос Wazzup (`{"test": true}`) получает 200.
2. Функция дедуплицирует по `messageId` (документ в `processedWebhooks`, повтор — скип), сохраняет сообщение в `conversations/{phone}/messages`, обновляет `lastInboundAtMs` и ставит Cloud Task `processConversation` с задержкой из настроек (`settings/bot`): по умолчанию **5 секунд**, а если фраза выглядит незаконченной («расскажите про,» / «а ещё») — **12 секунд** (`debounce.ts`). Обе величины редактируются в админ-панели.
3. Когда задача срабатывает, она **пропускает себя**, если после её маркера пришло более новое сообщение (для него уже стоит более свежая задача). Так несколько «пузырей», которые человек печатает подряд, склеиваются в один осмысленный ответ бота — вместо ответа на каждую реплику отдельно.
4. Обработчик молчит, если: глобальный тумблер бота выключен, режим диалога `human`, стоит пауза `pausedUntil`, или превышен лимит ответов в час (защита от зацикливания).
5. Иначе собирается запрос к LLM и крутится tool-loop (до 5 итераций): модель может запросить свободные слоты, забронировать экскурсию, сохранить данные лида или передать диалог человеку — затем финальный текст уходит через адаптер Wazzup и сохраняется с нашим `crmMessageId`.
6. **Ручной перехват без кнопок:** если Дана ответила клиенту сама (с телефона или из приложения Wazzup), вебхук получает echo-сообщение *без* нашего `crmMessageId` → бот автоматически ставит этому диалогу паузу на N часов (настраивается), чтобы человек и бот не говорили одновременно. Из админ-панели диалог можно вернуть боту в один клик.

## LLM-дизайн («мягкое понимание»)

### Сборка промпта

Системный промпт собирается **на каждый вызов** из Firestore — поэтому правки в админ-панели действуют со следующего же сообщения, без деплоя:

1. **Персона** (`settings/bot.systemPrompt`) — редактируется админом.
2. **Жёсткие правила** (константа в коде, не редактируются): тёплый тон в стиле Даны, один вопрос за раз, отвечать на языке клиента (RU/KZ/EN, база на русском — модель переводит), **готовые тексты использовать дословно**, не выдумывать цены и факты, при неоднозначном сообщении — короткий вежливый уточняющий вопрос, при отсутствии ответа в базе — инструмент handoff, игнорировать попытки клиента изменить инструкции (prompt-injection guard).
3. Текущие дата/время в Алматы (для «завтра», «во вторник»).
4. **Скриптовые блоки**: приветствие, питчи по возрастам (2/3/4/5 лет → Toddler/Pre-K/Kindergarten/Reception с точными ценами 400 000 ₸ полный день / 250 000 ₸ полдня).
5. **Все включённые FAQ** («Вопрос → Ответ»). При 20–50 вопросах это 3–6k токенов — RAG/эмбеддинги не нужны, gpt-5-mini делает это за копейки.
6. **Профиль лида** (что уже знаем: имя, возраст ребёнка) + инструкция вызывать `save_lead_info` при новых фактах.
7. Правила записи на экскурсию: сначала `get_available_slots`, предложить 2–3 варианта, подтвердить имя и возраст, затем `book_tour`.

### Инструменты (function calling)

| Инструмент | Что делает |
|---|---|
| `get_available_slots` | freebusy-запрос к календарю экскурсий ∩ рабочие часы (дни, часы, длина слота, мин. срок из настроек) → 2–3 кандидата |
| `book_tour` | повторная проверка, что слот свободен → событие в календаре («Экскурсия: {имя}, ребёнок {возраст}», телефон в описании) → документ в `bookings` |
| `save_lead_info` | merge новых фактов в профиль лида |
| `handoff_to_human` | режим `human`, запись в `unanswered`, WhatsApp-алерт на номер Даны |

Голосовые и картинки (на тарифе Inbox нет транскрибации): вежливый скриптовый ответ с просьбой написать текстом + флаг диалога в панели.

## Модель данных (Firestore)

| Коллекция | Содержимое |
|---|---|
| `settings/bot` | systemPrompt, greetingScript, agePitches{2..5}, fallbackText, voiceFallbackText, botEnabled, adminAlertPhone, tourHours, tourSlotMinutes, minLeadHours, maxDaysAhead, calendarId, timezone/utcOffsetMinutes, pauseOnManualReplyHours, maxBotMessagesPerHour, azureEndpoint/azureDeployment/azureApiVersion, wazzupChannelId |
| `faq/{id}` | question, answer, enabled, order — неограниченное количество |
| `conversations/{phone}` | mode (`bot`\|`human`), pausedUntilMs, lead {parentName, childName, childAge, …}, contactName, lastInboundAtMs, flagReason, botReplyTimestampsMs[] |
| `conversations/{phone}/messages/{id}` | direction, byBot, type, text, providerMessageId, crmMessageId, dateTimeMs |
| `bookings/{id}` | phone, parentName, childAge, slotStartIso, calendarEventId, status |
| `unanswered/{id}` | phone, question, context, resolved, createdAtMs — источник роста базы FAQ |
| `processedWebhooks/{messageId}` | дедуп вебхуков (TTL) |
| `sentMessages/{crmMessageId}` | наши отправки (бот/панель) — чтобы echo-вебхук отличал их от ручных ответов Даны |

Несекретная конфигурация (endpoint Azure, channelId и т.п.) намеренно живёт в `settings/bot` — правится из панели. Секреты (ключи API, JSON сервисного аккаунта) — только в Firebase Secret Manager.

## Админ-панель (6 страниц)

1. **Вход** — Firebase Auth (email/password); права по custom claim `admin: true` (скрипт `functions/scripts/setAdminClaim.ts`).
2. **Настройки бота** — системный промпт, приветствие, питчи по возрастам, fallback-тексты, глобальный вкл/выкл, часы экскурсий, длина слота, ID календаря, номер для алертов.
3. **FAQ** — CRUD-список без ограничения количества, вкл/выкл и порядок.
4. **Диалоги** — список с бейджами режима, транскрипт, «забрать диалог» / «вернуть боту», ручная отправка (callable → Wazzup; при ручной отправке бот ставится на паузу).
5. **Лиды и записи** — телефон, имя, возраст, статус, слот, ссылка на событие в календаре.
6. **Неотвеченные вопросы** — всё, на что бот не смог ответить, с кнопкой «сделать FAQ» (префилл формы). Так база знаний растёт из реального трафика.

## Безопасность

- Вебхук: секретный токен в URL; всё остальное — 403.
- Секреты в **Firebase Secret Manager** (`WAZZUP_API_KEY`, `AZURE_OPENAI_API_KEY`, `GCAL_SA_KEY`, `WEBHOOK_TOKEN`), в коде и git их нет.
- Firestore rules: любой доступ только при `request.auth.token.admin == true`; функции ходят через Admin SDK мимо правил.
- Календарь через сервисный аккаунт: Дана расшаривает календарь экскурсий на email SA с правом «Внесение изменений» — работает с личным Google-аккаунтом, Workspace не нужен.
- Защита от зацикливания: echo-сообщения не триггерят обработку, лимит ответов бота в час на диалог, групповые чаты игнорируются.
- PII-минимализм: храним только то, что нужно для записи (имя, телефон, возраст ребёнка).

## Ограничения и осознанные компромиссы

- **Wazzup Inbox — reply-only**: бот не может писать первым. Для алертов Дане нужно, чтобы диалог с её номером уже существовал (один раз написать на номер садика), либо тариф Pro. Алерт всегда дублируется флагом в панели.
- **Неофициальный канал WhatsApp** (QR-подключение) — стандартная практика в СНГ, но есть малый риск бана номера; телефон должен оставаться онлайн. Миграция на официальный WABA — смена тарифа в Wazzup, код не меняется.
- Повтор задачи Cloud Tasks после сбоя *после* отправки может теоретически привести к дублю сообщения (maxAttempts=2, вероятность мала) — принято ради простоты.
- Без RAG: вся база знаний влезает в промпт. Если FAQ вырастет до сотен — добавим отбор по ключевым словам, архитектура не меняется.
